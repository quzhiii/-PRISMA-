# 系统综述工作台视觉方向与命名建议

**日期：** 2026-07-13  
**状态：** 设计探索，不进入当前开发主线  
**适用时点：** 产品名称、入口、双审语义和 Methods 页面稳定之后

---

# 1. 视觉定位

建议将产品视觉定位为：

> **Research Operations Console**  
> 面向系统综述的研究流程与证据控制台

关键词：

- 可靠；
- 清晰；
- 可恢复；
- 证据导向；
- 本地数据主权；
- 方法学克制；
- 现代但不“AI 炫技”。

避免：

- 赛博朋克；
- 大面积荧光；
- 聊天机器人头像；
- 星空拓扑作为主界面；
- 玻璃拟态堆叠；
- 每一块内容都做成卡片；
- 用动画掩盖复杂状态；
- 把 AI 放在页面视觉中心。

---

# 2. 核心布局

## 2.1 工作台采用三栏结构

```text
┌──────────────┬──────────────────────────┬──────────────────┐
│ Stage Rail   │ Evidence Workspace       │ Context Panel    │
│ 项目阶段      │ 表格 / 记录 / 全文        │ 详情 / 建议 / 历史 │
└──────────────┴──────────────────────────┴──────────────────┘
```

### 左栏：阶段与状态

- 项目概览；
- Import；
- Deduplication；
- Title/Abstract；
- Full text；
- Quality；
- Export；
- 每阶段待处理数；
- 阻塞状态；
- 当前 checkpoint。

### 中栏：主工作区域

- 数据表；
- 筛选卡；
- 冲突队列；
- 质量评价表；
- 导出预览。

### 右栏：上下文面板

- 当前记录详情；
- 原始字段；
- 来源与文件；
- 决策历史；
- Reviewer A/B；
- AI 建议及来源；
- 审计链接。

不要使用弹窗承载核心工作。Modal 只用于确认、导入或短表单。

---

# 3. 首页结构

首页保持 publication-grade，不做复杂产品演示。

```text
1. 一句话定义
2. 三个开始入口
3. 四项核心差异
4. 真实工作流截图
5. 方法与证据
6. Demo / GitHub / 用户测试
7. 独立项目声明
```

## 三个入口

```text
开始一个综述
进入双人复核
准备方法与证据附件
```

如果名称改为 EvidenceDock：

```text
EvidenceDock
Local-first systematic review screening and evidence workspace.

本地优先的系统综述筛选与证据工作台。
```

# 4. 首页 Hero 建议

## 4.1 不使用抽象大标题

避免：

```text
重新定义 AI 科研
下一代智能研究
让研究无限生长
```

建议：

```text
把系统综述的筛选、复核和证据留痕放在同一个本地工作流里。
```

英文：

```text
Screen, reconcile, and preserve review evidence in one local-first workflow.
```

## 4.2 Hero 右侧不是装饰图

使用真实的产品状态预览：

- 当前阶段；
- 记录数量；
- 待复核冲突；
- 数据来源；
- 最近 checkpoint；
- 可导出证据。

---

# 5. 项目首页 / Project Pulse

进入项目后首先展示：

```text
项目阶段
已导入记录
疑似重复
待筛选
全文冲突
质量评价
最近保存
下一个建议动作
```

页面不是统计大屏，应突出：

1. 当前在哪里；
2. 什么阻塞了推进；
3. 下一步是什么；
4. 哪些状态已被保存；
5. 哪些建议需要人工确认。

---

# 6. 状态语义

建立统一状态语言。

| 类型 | 语义 | 建议表现 |
|---|---|---|
| Neutral | 未开始 / 普通信息 | 灰色 |
| Active | 当前阶段 / 进行中 | 蓝色或青绿色 |
| Confirmed | 人工确认 | 深绿色 |
| Suggested | AI 或规则建议 | 紫灰或蓝紫 |
| Conflict | Reviewer 冲突 | 琥珀色 |
| Blocking | 数据错误 / 无法继续 | 红色 |
| Archived | 历史 / 已替换 | 浅灰 |

AI 建议不得与人工确认使用同一颜色。

# 7. 组件建议

## 7.1 Stage Rail

- 细长纵向；
- 显示阶段状态；
- 可折叠；
- 当前阶段突出；
- 未满足前置条件时明确显示原因。

## 7.2 Evidence Table

- 固定标题列；
- 来源徽标；
- 关键字段可配置；
- 行内决策；
- 快捷键；
- 原始字段抽屉；
- 支持 facets / filter。

## 7.3 Record Inspector

右侧抽屉显示：

- 标题；
- 摘要；
- 作者与年份；
- 数据库来源；
- 原始文件；
- 匹配到的规则；
- Reviewer 决定；
- AI suggestion；
- 决策历史。

## 7.4 Audit Timeline

借鉴 OpenRefine 的 History：

- 按时间列出操作；
- 当前状态突出；
- 可进入历史 checkpoint；
- 影响条数；
- 操作者；
- 允许比较；
- 不轻易使用“撤销全部”。

## 7.5 Command Palette

适合高频用户：

```text
导入文件
打开冲突队列
保存 checkpoint
导出 Bundle
验证审计包
切换语言
```

# 8. 视觉风格

## 8.1 色彩

建议基底：

```text
背景：#F7F8F6 / #FFFFFF
主文字：#202421
次文字：#66706A
边框：#DDE2DE
主强调：低饱和青绿
信息：蓝灰
冲突：琥珀
错误：克制红
```

保留现有青绿色识别，但降低“整页浅绿卡片”的比例。

## 8.2 字体

当前页面使用 Google Fonts，会产生外部字体请求。既然产品强调 local-first，建议：

- 优先系统字体栈；
- 或将开源字体自托管；
- 中文使用系统黑体 / Noto Sans SC 自托管；
- 数字、hash、文件名使用等宽字体。

## 8.3 深浅模式

先完成浅色模式。深色模式在视觉系统稳定后增加。

科研工具的核心场景常包括：

- 长时间阅读；
- 表格；
- PDF；
- 打印或截图。

浅色模式的优先级更高。

## 8.4 动效

只用于：

- 面板切换；
- checkpoint 保存成功；
- 导入进度；
- 冲突解决；
- 状态更新。

不使用：

- 长时间背景漂浮；
- 光晕跟随；
- 复杂节点动画；
- 自动滚动 Agent 思考过程。

# 9. 可借鉴的视觉参考

## 9.1 Elicit

借鉴：

- 入口按用户任务区分；
- 研究问题 → 步骤化工作流；
- 表格与右侧任务状态并存；
- AI 作为具体步骤中的能力；
- 输出与来源保持连接。

避免照搬：

- 以自动生成报告为主叙事；
- 将云端检索和上传作为默认；
- 过度突出 Agent。

参考：

- https://support.elicit.com/en/articles/14757543-getting-started-with-elicit-which-workflow-or-tool-should-i-use

## 9.2 Linear

借鉴：

- 信息层级；
- 紧凑侧栏；
- status / label / progress 语义；
- 单一主操作；
- command palette；
- 项目概览和细节切换。

避免照搬：

- 纯深色主视觉；
- 过强的软件开发隐喻；
- 把研究阶段等同于 sprint。

参考：

- https://linear.app/docs/use-cycles

## 9.3 OpenRefine

借鉴：

- 数据表为中心；
- facet/filter；
- History 与主数据并列；
- 操作可撤销、重做和提取；
- 本地应用的工具感。

避免照搬：

- 老旧密集的视觉细节；
- 列级菜单过深；
- 对新手缺少引导。

参考：

- https://openrefine.org/docs/manual/running

## 9.4 Zotero

借鉴：

- 三栏信息架构；
- Library / Record / Detail；
- 本地桌面工具的稳定感；
- 来源、附件和笔记关系；
- 插件生态与核心 UI 分离。

避免照搬：

- 让产品看起来像文献管理器；
- 把文件夹树作为唯一项目结构。

参考：

- https://www.zotero.org/

## 9.5 ASReview

借鉴：

- 筛选任务聚焦；
- AI 与人工 label 的交互；
- simulation / benchmark 独立；
- 用户入口按角色拆分。

避免照搬：

- 将主动学习作为产品唯一中心；
- 以“节省百分比”作为未经本项目验证的承诺。

参考：

- https://asreview.nl/

# 10. 命名视觉方向

## EvidenceDock

视觉隐喻：

- dock / station；
- 文件进入、处理、交接和离开；
- 模块接口；
- 稳定基座。

Logo 可探索：

- 两个相接的矩形或文件层；
- 一条进入 Dock 后形成可追溯节点的线；
- 不使用 PRISMA 三角形；
- 不使用医院十字；
- 不使用机器人。

## SiftTrail

视觉隐喻：

- 多条记录经过筛选后保留一条轨迹；
- 决策节点；
- trail / path；
- 过滤与留痕。

风险：

- 容易做成漏斗图；
- 漏斗视觉与普通营销分析工具相似。

## ReviewTrail

视觉隐喻：

- review path；
- decision ledger；
- 多评审合流。

风险：

- 通用；
- 品牌识别度较弱。

# 12. 视觉验收标准

- 首页 60 秒可理解；
- 工作台 5 秒可定位当前阶段；
- AI 建议与人工决定不可混淆；
- 冲突和阻塞状态不可混淆；
- 每个页面只有一个主操作；
- 关键工作不依赖 Modal；
- 1280px、1440px 和移动端可用；
- 键盘操作可完成主要筛选；
- 表格密度可调；
- 无不必要外部请求；
- 截图可用于论文、答辩和文档；
- 不出现 PRISMA 官方品牌暗示。

# 13. 给视觉 Agent 的研究 Prompt

```text
请基于本文件先做视觉研究和低保真方案，不直接改动生产页面。

目标产品是本地优先的系统综述筛选与证据工作台。视觉定位为 Research Operations Console，强调研究流程、状态、证据、恢复和人工确认。

请参考 Elicit 的任务入口与表格/进度组合、Linear 的状态层级、OpenRefine 的数据表与历史、Zotero 的三栏结构、ASReview 的筛选任务聚焦。

产出：
1. 信息架构图；
2. 首页低保真；
3. Project Pulse 低保真；
4. 筛选工作区三栏低保真；
5. 双审冲突页低保真；
6. audit timeline；
7. design tokens；
8. AI suggestion / human confirmed / conflict / blocking 状态规范；
9. EvidenceDock、SiftTrail、ReviewTrail 三个名称的简单 wordmark 方向。

限制：
- 不使用赛博朋克、机器人、发光粒子、星空主界面；
- 不以聊天框作为主交互；
- 不改变当前 workflow engine；
- 不引入账号、云同步和数据库爬虫；
- 不直接生成生产代码。
```

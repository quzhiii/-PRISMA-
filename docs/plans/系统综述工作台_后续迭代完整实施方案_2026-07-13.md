# 系统综述工作台后续迭代完整实施方案

**日期：** 2026-07-13  
**依据文档：**

- `docs/plans/系统综述工作台_后续迭代路线图与开源生态借鉴_2026-07-13.md`
- `docs/plans/系统综述工作台_视觉方向与命名建议_2026-07-13.md`

**当前基线：** PRISMA Workbench V2.5 公开线，`literature-screening-v2.2/` 作为当前兼容发布路径  
**执行定位：** 把“能力已较完整的本地工具”收敛成“版本清晰、入口一致、证据边界明确、可恢复、可验证、可扩展的系统综述工作台”  
**本方案用途：** 后续本地 Agent、维护者、用户测试协作者的执行蓝图

---

## 1. 总体判断

当前产品的工程能力已经超过公开叙事的清晰度。真正的下一步不是继续堆功能，而是先完成四个收敛：

1. **公开面收敛**：版本、路由、README、官网、资源页、工作台入口必须说同一件事。
2. **协作语义收敛**：双人复核是 file-based local-first bundle round-trip，不是账号登录或实时协作。
3. **证据边界收敛**：不再使用 `audit-ready`、官方暗示和绝对化承诺，用 Methods 页面承接验证证据、限制和复现路径。
4. **架构扩展收敛**：中文数据库、模板、AI、CLI 和未来视觉系统都通过契约和 registry 接入，不能继续侵入主流程。

因此，后续迭代应拆成四条 release train：

| Release Train | 覆盖阶段 | 核心目标 | 是否先做 |
|---|---|---|---|
| RT-0 Public Alignment | M0-M2 | 冻结基线、统一公开版本、准备命名测试 | 必须最先 |
| RT-1 Workflow Trust Core | M3-M5 | `/start/`、双审 round-trip、`/methods/` 证据体系 | 本轮主线 |
| RT-2 Extensibility Foundation | M6-M11 | adapters、history/replay、registry、CLI、检索日志、社区机制 | 主线稳定后 |
| RT-3 Visual System | M12/V-0-V-5 | Research Operations Console 视觉系统 | 最后启动 |

---

## 2. 本轮硬边界

### 2.1 本轮必须做

- 公开面审计和风险清单。
- 当前公开版本统一为 `2.5`，将 V2.6/V2.7/V3.0 改成能力切片或内部资产。
- 对外文案去除官方暗示、绝对承诺和超出证据边界的表达。
- 建立 `/start/`，把 Demo、新建导入、恢复已有项目作为统一入口。
- 重构 `login.html` 语义为双人复核设置，不再暗示账号、加入项目或同步等待。
- 固化 Reviewer Seed Bundle / Decision Bundle / Merge / Resolver 的 round-trip contract 和测试。
- 建立 `/methods/`，展示当前实现、验证证据、已知限制、benchmark、数据保真、双审完整性、AI 边界和复现。
- 形成命名测试材料，但不直接改仓库名、域名或数据 producer。

### 2.2 本轮明确不做

- 不做 AI 聊天式主界面。
- 不做大规模视觉重构。
- 不做账号、登录、支付、多租户、云同步或实时协作。
- 不做数据库爬虫。
- 不做模板市场。
- 不让 AI 自动替代人工纳排。
- 不把 Stello/KitKit 直接接进核心 review ledger。
- 不用 memory 或聊天摘要承载项目真实状态。


## 4. 推荐执行顺序

```text
Phase 0  准备独立 worktree / 分支
Phase 1  M0 公开面与运行时基线审计
Phase 2  M1 公开版本、路由、声明和禁用词收敛
Phase 3  M2 命名测试材料和迁移预案，不正式重命名
Phase 4  M3 /start/ 与项目入口模型
Phase 5  M4 双人复核 Bundle 语义与 round-trip
Phase 6  M5 /methods/ 与验证证据体系
Phase 7  主线 closeout：全量测试、预览、用户确认、暂停
Phase 8  M6-M11 独立 worktree 分批推进
Phase 9  M12 视觉系统升级
```

关键原则：M0-M5 是一个完整闭环，应优先一次性做完；M6-M12 必须在主线 closeout 后拆分推进。

## 6. M1：统一公开版本、路由和边界文案

### 6.1 目标

用户打开任一入口，都只能理解为：当前公开版本是 V2.5；V2.6/V2.7/V3.0 是能力切片或内部资产，不是并列公开版本；项目独立于 PRISMA 官方组织；AI 只提供建议，人工决定才进入最终 ledger。

### 6.2 路由目标

| 目标路径 | 页面定位 | 初始实现方式 |
|---|---|---|
| `/` | 当前官网和产品定义 | 保持静态入口，统一 CTA |
| `/app/` | 工作台 | 指向现有 `literature-screening-v2.2/workspace.html` 或兼容跳转 |
| `/start/` | 开始与恢复 | M3 新增 |
| `/dual-review/` | 双人复核设置 | M4 新增或由 `login.html` 兼容跳转 |
| `/resources/` | 用户资源 | 从现有 resources 拆分 |
| `/methods/` | 方法、证据、限制 | M5 新增 |
| `/legacy/` | 历史版本 | 先做静态索引或兼容说明 |

如果当前静态部署不方便立即新增目录路由，可以先用目录中的 `index.html` 或 compatibility link 实现。

### 6.3 文案替换规则

| 旧表达 | 新表达 |
|---|---|
| audit-ready | audit-oriented / designed for traceability |
| 可审计工作台 | 可追溯、面向复核的工作台 |
| 答辩级审计包 | 答辩与方法附录证据包 |
| 确保符合 PRISMA | 支持生成 PRISMA 2020 所需的流程计数与导出 |
| AI 自动筛选 | AI 筛选建议 |
| 绝对安全 | 默认本地处理；具体边界见数据说明 |
| 登录 | 双人复核设置 / 导入 Reviewer Bundle |
| 加入项目 | 导入 Reviewer Bundle |
| 等待同步 | 等待对方导出 Decision Bundle |

### 6.4 独立项目声明

所有公开页面页脚或 Methods 中应加入：


英文版：

```text
This project is an independent open-source tool and is not affiliated with, endorsed by, or certified by the PRISMA Statement organization. PRISMA is a reporting guideline for systematic reviews.
```

- 根入口和 `literature-screening-v2.2/` 的版本展示一致。

### 6.6 验收标准

- 根入口只展示当前公开版本 `2.5`。
- 页面中无 V3 正式发布误导。
- 旧版本进入 `/legacy/` 或明确标为历史兼容路径。

## 7. M2：命名测试与迁移预案

### 7.1 目标

本阶段只准备命名测试，不做正式重命名。正式改名会影响仓库、域名、CLI、schema producer、export manifest 和用户认知，必须等 5-8 人测试后再决定。

| ReviewTrail | 综述轨迹 | 理解成本低 | 通用词强，品牌占位弱 |

## 8. M3：建立 `/start/` 与项目入口模型

### 8.1 目标

用户进入产品后不再被历史页面、版本路径和双审入口分散，而是看到三个起点：体验 Demo、新建项目并导入、恢复已有项目。

### 8.2 页面结构

```text
/start/
├── 体验 Demo
├── 新建项目并导入
└── 恢复已有项目
```

进入项目后再选择：

```text
单人筛选
双人独立筛选
```

不要在入口阶段提前让用户选择质量评价、审计包或 Methods 附件等下游任务。

### 8.3 状态合同

```ts
type StartMode = "demo" | "new-import" | "resume";
type ReviewMode = "single" | "dual";

type ProjectStage =
  | "empty"
  | "import"
  | "deduplication"
  | "title-abstract"
  | "full-text"
  | "quality-appraisal"
  | "export";
```

### 8.4 每个入口卡片必须说明

- 适用场景。
- 用户需要准备什么。
- 数据是否离开设备。
- 将进入哪个阶段。
- 是否可撤销。
- 会产生哪些文件。

### 8.5 实现建议

| 任务 | 建议路径 | 说明 |
|---|---|---|
| 新增 start 页面 | `start/index.html` 或 `literature-screening-v2.2/start.html` | 先保持静态部署简单 |
| 新增入口脚本 | 可复用现有 `app.js` 中项目加载逻辑，避免重写核心 | 入口层只分流 |
| 恢复诊断 | 对项目包进行 schema、producer、version、manifest 基础检查 | 不要静默失败 |
| CTA 调整 | 根入口、README、landing、resources 都指向 `/start/` | 消除旧入口混乱 |

### 8.6 测试

- Demo 可进入且不污染本地已有项目。
- 新建导入进入 import 阶段。
- 恢复已有项目跳过 onboarding。
- 无效项目包给出诊断而不是崩溃。
- 单人/双人选择不会改变已存在项目的历史决定。

### 8.7 验收标准

- 5 秒内能理解从哪里开始。
- 三个入口都可完成基本路径。
- 数据本地边界清楚。
- 入口可用于第一轮用户测试。

## 9. M4：双人复核 Bundle 语义与 Round-trip

### 9.1 目标

把当前双人复核从“像登录页”的表象，改成真实的 file-based local-first reviewer bundle 工作流。

### 9.2 页面改名和文案替换

| 当前语义 | 新语义 |
|---|---|
| `login.html` | `dual-review/` 或兼容跳转到双人复核设置 |
| 登录 | 双人复核设置 |
| 加入项目 | 导入 Reviewer Bundle |
| 等待同步 | 等待对方导出 Decision Bundle |
| 账号/会话 | reviewer ID / bundle file |

### 9.3 角色流程

项目负责人：

```text
创建项目
→ 冻结评审 Seed
→ 导出 Reviewer A / Reviewer B Bundle
→ 收集两个 Decision Bundle
→ 验证并合并
→ 进入冲突解决
→ 导出最终证据
```

Reviewer：

```text
导入 Reviewer Bundle
→ 验证 project ID / reviewer ID / schema / hash
→ 独立筛选
→ 导出 Decision Bundle
```

### 9.4 Bundle Contract

至少固化：

```json
{
  "bundle_type": "reviewer-seed | reviewer-decision",
  "schema_version": "1.x",
  "project_id": "uuid",
  "reviewer_id": "A",
  "created_at": "...",
  "source_manifest_hash": "...",
  "record_count": 0,
  "decisions_hash": "...",
  "producer": "...",
  "producer_version": "..."
}
```

### 9.5 必须验证

- Bundle 类型正确。
- Project ID 匹配。
- Schema 兼容。
- Reviewer ID 未重复合并。
- Source manifest hash 匹配。
- Record count 匹配。
- Decisions hash 可重算。
- 缺失记录、非法修改、重复合并可拒绝。
- 合并后冲突数量可重算。

### 9.6 Round-trip Fixture

```text
Project → Seed A/B
Seed A → Decisions A
Seed B → Decisions B
A+B merge → Conflict queue
Resolve → Final decisions
Final decisions → Export
Export counts → Replay counts
```

每一步都要有 fixture 和 hash 断言。

### 9.7 实现建议

| 任务 | 建议路径 |
|---|---|
| 固化 pure helper | `reviewer-bundle-engine.js` |
| UI 文案改造 | `login.html`、`literature-screening-v2.2/login.html` |
| 工作台导出/导入入口 | `workspace.html`、`app.js` |
| 测试 | `tests/audit/reviewer-bundle-engine.test.mjs` 新增 round-trip cases |
| Fixture | `tests/fixtures/reviewer-bundle-roundtrip/` |

### 9.8 验收标准

- 用户不会误认为存在在线登录或实时同步。
- 合法 A/B bundle 可合并并进入 resolver。
- 非法、重复、缺失、hash 不匹配的 bundle 被拒绝并给出诊断。
- Export counts 可从 ledger 和 replay 重新得到。

## 10. M5：建立 `/methods/` 与验证证据体系

### 10.1 目标

用 Methods 页面替代夸张营销承诺。公开展示当前实现、验证证据、限制、benchmark、数据保真协议、双审完整性协议、AI 边界、版本与复现。

### 10.2 页面结构

```text
/methods/
├── 当前实现
├── 当前验证证据
├── 已知限制
├── Benchmark
├── 数据保真协议
├── 双审完整性协议
├── AI 边界
└── 版本与复现
```

### 10.3 证据分层

| 层级 | 含义 | 初始材料 |
|---|---|---|
| E1 功能回归 | 单元/集成/回归测试 | `tests/run-all-regressions.js` |
| E2 数据保真 | 导入字段、原始值、编码、source mapping | import fixtures、Chinese source tests |
| E3 算法表现 | 去重 precision/recall/F1、误合并率 | dedup benchmark docs |
| E4 工作流完整性 | dual-review、bundle、replay、export count | reviewer bundle round-trip |
| E5 外部项目验证 | 真实脱敏项目和用户测试 | 暂标 planned，不虚构 |

### 10.4 指标定义

导入：

- 字段保存率。
- 编码识别率。
- 来源识别率。
- 解析失败可诊断率。
- 原始值保留率。

去重：

- precision。
- recall。
- false merge rate。
- missed duplicate rate。
- 自动合并与候选合并分开报告。

双审：

- Seed/Decision round-trip 一致性。
- 冲突重放一致性。
- resolver 后计数一致性。
- 重复合并检测。
- 非法 Bundle 拒绝率。

导出：

- 相同项目重复导出的语义一致性。
- PRISMA 计数可由 decision ledger 重算。
- manifest 和文件 hash 完整。
- 导出版本可追踪。

### 10.5 AI 边界说明

Methods 中必须明确：

- AI 默认关闭。
- AI 输出是 advisory-only。
- AI 建议必须带来源、时间、配置、prompt/input hash 和人工确认状态。
- AI 不直接写最终 `ScreeningDecision`。
- AI 建议与人工确认不能使用同一颜色或状态语义。

### 10.6 验收标准

- Methods 页面可直接解释为什么不再说 `audit-ready`。
- 当前已有证据和计划中证据分开，不虚构外部验证。
- Benchmark 数字能追溯到仓库文件。
- 用户能理解本地数据边界、双审边界和 AI 边界。

## 12. M6：Source Adapter / Importer 架构

### 12.1 启动条件

- M0-M5 已 closeout。

### 12.4 Adapter Contract

```ts
interface SourceAdapter {
  id: string;
  label: string;
  version: string;
  sourceFamily: string;
  supportedExtensions: string[];
  detect(input: AdapterInput): DetectionResult;
  parse(input: AdapterInput): ParseResult;
```

## 13. M7：历史、Checkpoint 与 Replay

### 13.1 目标

统一区分 Project Schema Version、Project State Version、Operation History、Review Run、Export Snapshot，形成可恢复、可解释和可重放的项目历史模型。

### 13.2 数据模型建议

```ts
interface ProjectCheckpoint {
  checkpointId: string;
  projectId: string;
  parentCheckpointId?: string;
  createdAt: string;
  stage: ProjectStage;
  stateHash: string;
  eventCursor: number;
  label?: string;
}

interface ReviewEvent {
  eventId: string;
  projectId: string;
  sequence: number;
  type: string;
  actor: ActorRef;
  createdAt: string;
  payload: unknown;
  previousHash?: string;
}
```

### 13.3 UI 要求

History UI 显示：

- 操作名称。
- 操作者。
- 时间。
- 影响记录数。
- 可否撤销。
- 相关导出。
- 相关 AI 建议。
- checkpoint label。

### 13.4 禁止事项

- 禁止用聊天摘要替代操作历史。
- 禁止让 AI suggestion 直接变成最终决定。
- 禁止让导出包反向成为唯一项目数据源。

### 13.5 验收标准

- 任一 checkpoint 可验证 state hash。
- Replay 后 PRISMA counts 与导出 counts 一致。
- Rollback 后 hash 与历史 checkpoint 一致。
- History UI 能解释当前状态从何而来。

## 15. M9：本地 CLI 与 Agent Bridge

### 15.1 启动条件

- M6 adapter contract 初步稳定。
- M7 event/checkpoint/replay 模型初步稳定。
- Methods 页面已有验证口径。

### 15.2 CLI 定位

工作名：`reviewctl`

目标：让本地 Agent 能读取项目状态、执行确定性检查、生成建议和验证导出，但不能绕过人工决策。

### 15.3 第一批只读命令

```bash
reviewctl project inspect <project>
reviewctl project status <project> --json
reviewctl import validate <file>
reviewctl bundle verify <bundle>
reviewctl audit verify <export-dir>
reviewctl methods report <project>
```

### 15.4 第二批可写命令

所有写操作必须：默认 dry-run、输出 patch、用户确认、记录 actor、生成事件、可回滚。

```bash
reviewctl import apply <file> --confirm
reviewctl project checkpoint <project>
reviewctl bundle merge <bundle> --dry-run
reviewctl assistant suggest-dedup <project>
```

### 15.5 不做事项

- CLI 登录。
- 云端 Space。
- 多租户。
- 远程执行。
- 自动改写最终纳排。
- Agent 直接删除记录。

### 18.4 状态语义

| V-3 | 筛选工作区：table/card 切换、inspector、decisions、keyboard、AI provenance |
| V-4 | 双审与历史：A/B 状态、Bundle、conflict、resolver、timeline |

- 不把聊天框作为主交互。

## 20. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 版本口径越改越乱 | 用户不知道使用哪个版本 | M0 先审计，M1 只保留 Current public release 2.5 |
| 品牌重命名过早 | 链接、schema、用户认知断裂 | M2 只做测试材料，正式迁移另开分支 |
| 双审页面继续像登录 | 用户误以为有账号和实时协作 | M4 全面改为 Bundle handoff 语义 |
| Methods 页面变成营销页 | 继续超出证据边界 | 按 E1-E5 分层，planned 与 verified 分开 |
| Adapter 抽离一次性过大 | 导入回归风险高 | M6 先迁移一个标准格式和一个中文源样板 |
| History/replay 与现有快照冲突 | 恢复行为不可预测 | M7 先定义版本概念和 hash，不急于重写 UI |
| CLI 过早写操作 | Agent 绕过人工决策 | M9 第一批只读，可写命令默认 dry-run |
| 视觉先行 | 好看但语义更乱 | M12 等名称、入口、Methods、用户测试后启动 |

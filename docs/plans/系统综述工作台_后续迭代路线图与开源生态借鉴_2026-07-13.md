# 系统综述工作台后续迭代路线图与开源生态借鉴

**日期：** 2026-07-13  
**适用对象：** 本地开发 Agent、产品维护者、后续用户测试协作者  
**当前基线：** PRISMA Workbench V2.5 公开线  
**执行原则：** 先统一产品语义和数据契约，再扩展功能；视觉重构单独立项，不作为本轮主线。

---

## 0. 文档目的

本文件承接当前 V2.5 版本，整理后续迭代的优先级、任务依赖、工程产出、测试要求和暂停边界，并分析 KitKit / Stello、Zotero、OpenRefine、ASReview、LangGraph、n8n、Dify 等开源产品或生态中可借鉴的机制。

本轮目标：

> 把当前“能力较完整但公开叙事和工程边界仍不统一的工具”，推进为“版本清晰、入口一致、可恢复、可验证、可扩展的本地优先系统综述工作台”。

本轮不以以下事项为主：

- AI 聊天式界面；
- 大规模视觉改版；
- 实时云协作；
- 用户账号和支付；
- 数据库爬虫；
- 模板市场；
- 多租户服务端；
- 自动替代人工纳排。

# 1. 当前关键问题

## 1.1 公开版本和入口不统一

当前公开表面存在：

- V2.5 当前稳定线；
- V2.6 / V2.7 能力切片；
- V3 资源中心；
- V3.0 发布准备资产；
- 历史路径中仍含 `v2.2`；
- GitHub Pages 根入口可能继续暴露旧页面。

### 风险

- 用户无法判断正在使用哪个版本；
- README、官网、工作台、资源页产生不同预期；
- V3 被理解为已经正式发布；
- 后续错误报告难以定位到真实构建。

## 1.2 公开文案超过现有证据边界

重点包括：

- `audit-ready`；
- “可审计”作为整体产品认证式表述；
- “PRISMA 官方”或官方关系暗示；
- “绝对安全”“完美支持”“完全保障”等绝对化承诺；
- 内部回归测试被误解为真实项目验证。

## 1.3 双人复核页面与真实协作机制不一致

当前真实机制更接近：

```text
项目负责人导出 Seed Bundle
→ Reviewer A / B 分别处理
→ 导出 Decision Bundle
→ 项目负责人合并
→ Resolver 处理冲突
```

如果页面仍使用“登录、加入项目、等待同步”等语言，会让用户误认为存在在线账号和实时同步。

## 1.4 资源、方法证据、内部研发材料混合

目前资源中心混合：

- 用户 Demo；
- 工作流模板；
- benchmark；
- 软件论文准备材料；
- 未实现功能的设计文档。

这些内容的目标读者和成熟度不同，需要拆分。

## 1.5 数据导入兼容能力仍偏内建逻辑

中文数据库兼容是核心差异，但如果解析规则持续写进主工作流，会导致：

- 新增来源成本升高；
- 测试范围膨胀；
- 社区贡献困难；
- 单个来源变动影响整个构建。

## 1.6 项目历史、事件日志与“可恢复”能力还未形成统一模型

当前已有快照、事件、回滚、Bundle 等能力，但后续需要统一区分：

- 项目状态版本；
- 操作历史；
- 运行记录；
- 人工决定；
- AI 建议；
- 导出快照；
- 文件交换记录。

# 2. 总体产品架构

后续架构保持四层分离。

```text
┌────────────────────────────────────────────┐
│ Public Surface                             │
│ 官网 / Start / Resources / Methods / Docs  │
├────────────────────────────────────────────┤
│ Review Application                         │
│ 导入 / 去重 / 筛选 / 双审 / 质量评价 / 导出 │
├────────────────────────────────────────────┤
│ Deterministic Review Core                  │
│ typed state / event ledger / checkpoints   │
│ decisions / bundles / validation           │
├────────────────────────────────────────────┤
│ Optional Extensions                        │
│ source adapters / templates / local agents │
│ CLI / AI advisory providers                │
└────────────────────────────────────────────┘
```

### 架构原则

1. **确定性核心优先。**
   系统综述项目的真实状态不能依赖聊天记录或模型记忆。

2. **事件、状态和导出分离。**
   当前状态可由事件与快照恢复，但导出物不能反向成为唯一数据源。

3. **扩展通过契约接入。**
   中文数据库解析、模板、AI provider、CLI 不能直接侵入核心数据模型。

4. **所有 AI 能力保持 advisory-only。**
   AI 输出必须带来源、时间、配置和人工确认状态。

5. **本地优先不等于拒绝扩展。**
   可以设计 BYO API、CLI 和后续自托管，但默认流程不依赖云端。

# 6. M2：产品命名决策与迁移

## 6.1 命名目标

新名称应满足：

- 不直接暗示 PRISMA 官方关系；
- 能覆盖未来的检索记录、筛选、双审和证据导出；
- 能被研究生和方法学人员快速理解；
- 具备可记忆性；
- 英文拼写较短；
- 可形成清楚的中文描述；
- 便于仓库、CLI、数据格式和页面使用。

## 6.2 当前候选

### A. EvidenceDock

中文工作描述：

```text
EvidenceDock｜证据工作台
```

优点：

- “Evidence”明确研究证据方向；
- “Dock”对应工作站、汇入、交接和扩展；
- 能容纳筛选之外的检索记录、质量评价和证据包；
- 初步 GitHub 精确名称搜索未发现同名仓库。

风险：

- 单看名称不能直接看出“系统综述”；
- 仍需完整域名、商标和软件目录检查。

### B. SiftTrail

中文工作描述：

```text
SiftTrail｜筛选轨迹
```

优点：

- 同时表达筛选和留痕；
- 初步 GitHub 精确名称搜索未发现同名仓库；
- 更贴近当前核心价值。

风险：

- `sift` 对部分中文用户不够直观；
- 产品未来扩展到检索和数据提取后可能略窄。

### C. ReviewTrail

中文工作描述：

```text
ReviewTrail｜综述轨迹
```

优点：

- 理解成本低；
- 能表达系统综述和过程留痕。

风险：

- GitHub 已存在多个近似或同名仓库；
- 通用词组合的品牌占位能力较弱。

### D. LitTrail / StudyLedger / ReviewTrace

当前不优先：

- 已发现精确或近似 GitHub 名称；
- `Ledger` 容易产生财务产品联想；
- `Lit` 对非英语母语用户可能不够直接。

## 6.3 建议的命名测试

不要直接重命名仓库。先进行 5–8 人快速测试：

每人只看名称和一句副标题，回答：

1. 你认为这是什么工具？
2. 你记得住这个名字吗？
3. 你觉得它偏向筛选、写作、检索还是数据管理？
4. 你会如何拼写？
5. 你是否误认为它是 PRISMA 官方软件？

测试版本：

```text
EvidenceDock
Local-first systematic review screening and evidence workspace.

SiftTrail
Traceable literature screening for systematic reviews.

ReviewTrail
A local-first workflow for systematic reviews.
```

## 6.4 迁移清单

命名确认后再执行：

```text
- repository display name
- package / app display name
- page title and meta
- logo label
- project schema product field
- export package producer field
- CLI command
- docs paths
- domain
- GitHub Pages
- legacy alias
- independent-project disclaimer
```

### 数据兼容

旧项目文件必须继续读取：

```json
{
  "producer": "PRISMA Workbench",
  "producer_version": "2.5"
}
```

新版本可以写：

```json
{
  "producer": "EvidenceDock",
  "producer_version": "2.6",
  "legacy_product_aliases": ["PRISMA Workbench"]
}
```

不要因品牌重命名强制升级数据 schema major version。

# 8. M4：重构双人复核语义与 Bundle Round-trip

## 8.1 页面改名

```text
login.html → dual-review/
登录 → 双人复核设置
加入项目 → 导入 Reviewer Bundle
等待同步 → 等待对方导出 Decision Bundle
```

## 8.2 角色流程

### 项目负责人

```text
创建项目
→ 冻结评审 Seed
→ 导出 Reviewer A / Reviewer B Bundle
→ 收集两个 Decision Bundle
→ 验证并合并
→ 进入冲突解决
```

### 复核员

```text
导入 Reviewer Bundle
→ 验证项目 ID / reviewer ID / schema
→ 独立筛选
→ 导出 Decision Bundle
```

## 8.3 Bundle Contract

至少包含：

```json
{
  "bundle_type": "reviewer-seed | reviewer-decision",
  "schema_version": "1.x",
  "project_id": "uuid",
  "reviewer_id": "A",
  "created_at": "...",
  "source_manifest_hash": "...",
  "record_count": 0,
  "decisions_hash": "...",
  "producer": "...",
  "producer_version": "..."
}
```

## 8.4 必须验证

- Bundle 来源；
- 项目 ID；
- schema 兼容；
- reviewer 是否重复；
- records hash；
- 是否已合并；
- 冲突数量；
- 非法修改；
- 缺失记录。

## 8.5 Round-trip 测试

```text
Project → Seed A/B
Seed A → Decisions A
Seed B → Decisions B
A+B merge → Conflict queue
Resolve → Final decisions
Final decisions → Export
Export counts → Replay counts
```

每一阶段都要有 fixture 和 hash 断言。

# 10. M6：Source Adapter / Importer 架构

## 10.1 借鉴 Zotero Translators

Zotero 将 Web、Import、Export、Search translator 拆为独立模块。每个 translator 包含：

- metadata；
- detection logic；
- parsing logic；
- test cases；
- stable ID；
- version / lastUpdated；
- priority。

本项目可建立：

```text
adapters/
├── ris/
├── nbib/
├── bibtex/
├── cnki/
├── wanfang/
├── vip/
└── sinomed/
```

## 10.2 Adapter Contract

```ts
interface SourceAdapter {
  id: string;
  label: string;
  version: string;
  sourceFamily: string;
  supportedExtensions: string[];
  detect(input: AdapterInput): DetectionResult;
  parse(input: AdapterInput): ParseResult;
  validate(records: CanonicalRecord[]): ValidationReport;
}
```

## 10.3 每个 Adapter 必须包含

```text
adapter.json
index.ts / index.js
fixtures/
tests/
known-limitations.md
mapping.md
LICENSE
```

## 10.4 adapter metadata

```json
{
  "id": "cnki-rdf",
  "label": "CNKI RDF Export",
  "version": "0.1.0",
  "priority": 100,
  "maintainers": [],
  "input_formats": ["rdf", "txt"],
  "last_updated": "2026-07-13",
  "license": "...",
  "status": "experimental"
}
```

## 10.5 社区贡献边界

本阶段只支持仓库内 Registry，不建立在线 marketplace。

贡献流程：

```text
Issue → fixture → adapter → tests → mapping doc → review → merge
```

# 11. M7：历史、Checkpoint、Replay

## 11.1 借鉴 OpenRefine

OpenRefine 的关键机制：

- 数据变更从项目创建起持续记录；
- 项目退出后历史仍保存；
- 项目归档包含历史；
- 用户可以在时间线上撤销和重做；
- 操作可提取为 JSON，并应用到其他项目。

适合本项目的映射：

```text
项目历史时间线
导入修复操作
去重操作
筛选规则变更
批量决定
冲突解决
质量评价修改
导出快照
```

## 11.2 借鉴 n8n

n8n 明确区分：

- workflow version；
- execution history；
- restore；
- clone；
- download JSON。

本项目也应区分：

```text
Project Schema Version
Project State Version
Operation History
Review Run
Export Snapshot
```

## 11.3 借鉴 LangGraph

LangGraph 的 checkpoint / interrupt 适合未来可暂停的 agent 流程，但不能直接替代当前 review core。

可借鉴：

- 持久 checkpoint；
- stable thread/project ID；
- human approval interrupt；
- resume；
- time travel；
- fault recovery。

## 11.4 建议数据模型

# 14. KitKit / Stello 借鉴边界

## 14.1 可以借鉴

### A. Workstream / Session 分支

系统综述项目可以拆成相互隔离的工作流：

```text
检索策略
导入与去重
标题摘要筛选
全文复核
质量评价
证据表
论文方法附录
```

每个工作流有独立上下文和输出，项目层汇总状态。

### B. Digest 与 Insight 分离

Stello 区分：

- Session 原始历史；
- memory：供外部 orchestrator 阅读；
- insight：定向回写的一次性信息。

本项目可以映射为：

```text
Raw project events
Stage digest
Reviewer / agent suggestion inbox
```

### C. 解耦

Stello 不绑定 LLM、存储和 UI。此方向适合本项目未来的 AI provider 层。

### D. Devtools

拓扑检查、事件回放和 prompt/settings 观察，可转化为本项目的：

- 项目状态检查器；
- Bundle 调试器；
- event replay；
- AI 建议 provenance viewer。

## 14.2 不应直接借鉴

### A. 星空拓扑作为主 UI

系统综述流程主要是阶段状态机，拓扑图可作为辅助视图，不能替代项目阶段和队列。

### B. memory 摘要作为真实状态

摘要存在有损压缩。Stello 自身公开 issue 也讨论了多次压缩、freshness 和错误综合污染风险。

项目决定必须保存在 typed ledger，不保存在 `memory.md`。

### C. 自动分支纳入核心筛选

自动 fork 适合探索性研究对话，不适合决定性的纳排流程。

### D. 立即引入 server / PostgreSQL / 多租户

这会破坏当前静态、本地优先的验证路径。

## 14.3 可选实验

在独立实验分支中测试：

```text
一个 review project
→ 多个 research workstream
→ 每个 workstream 生成 digest
→ 项目 orchestrator 汇总下一步建议
→ 建议进入人工确认 inbox
```

实验不得读写最终 decision ledger。

## 24. 研究结论边界

- 本文件中的命名检索仅为初步产品识别检查，不构成商标或法律意见。
- KitKit 的网站产品与 Stello 开源引擎应分别评价；前者是产品层，后者是基础能力层。
- Stello 当前仍在快速迭代，公开 issue 已显示跨 Session 信息损耗、freshness 和多模态等问题仍在讨论，不建议直接成为当前确定性 review core 的依赖。
- 开源项目中的机制只作为架构参考，不能直接证明适合系统综述方法学场景。
